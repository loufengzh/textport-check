# textport-check

Одни байты, несколько потребителей, разные ответы. CLI строит матрицу совместимости кодировки для явно выбранных потребителей и показывает противоречащие требования. Только чтение: без изменения файлов, угадывания старых кодировок, предпросмотра исходников и выполнения проверяемых скриптов.

[English](../README.md) · [简体中文](README.zh-CN.md) · [Deutsch](README.de.md)

Многоязычному скрипту Windows PowerShell 5.1 нужен UTF-8 BOM для переносимого чтения вне зависимости от старой кодовой страницы. Прямо запускаемый Unix-скрипт требует `#!` с нулевого байта. Политика «убрать все BOM» не описывает обе задачи. ASCII не требует BOM.

## Установка

Python 3.10+, без зависимостей времени выполнения. Установка из репозитория, публикация на PyPI не заявлена:

```sh
python -m pip install .
textport-check --profile powershell51-script --profile utf8-no-bom examples/greeting.ps1
textport-check --config examples/textport.json --format json
```

Первый пример намеренно возвращает 1 и показывает конфликт `TPC400`. Можно подготовить отдельные артефакты или изменить договорённость о потребителе; автоматического преобразования нет.

## Профили и ограничения

- `powershell51-script`: ASCII и корректный UTF-8 с BOM проходят проверку байтов. Не-ASCII UTF-8 без BOM несовместим с требованием переносимости при стандартных старых ANSI-кодовых страницах; на системе с UTF-8 кодовой страницей результат может отличаться. Некорректный UTF-8 без BOM неизвестен. BOM UTF-16/32 LE/BE распознаётся и строго проверяется, но поддержка чтения скрипта этим профилем не сертифицирована: результат неизвестен. Декодированный NUL также неизвестен.
- `posix-direct-script`: отсутствие BOM, `#!` в начале, непустая ASCII-строка интерпретатора с LF, тело ASCII/UTF-8 без NUL. BOM, отсутствие shebang и CR в первой строке несовместимы. Не-ASCII/незавершённая LF строка интерпретатора, NUL или другое кодирование тела дают неизвестный результат. Некоторые интерпретаторы допускают не-UTF-8 тело.
- `utf8-no-bom`: явно заданный договор проекта, корректный UTF-8 без BOM. Пустой файл и NUL допустимы. Это не утверждение, что все текстовые форматы запрещают BOM.

Совместимость означает лишь прохождение этих проверок байтов, а не правильность синтаксиса, безопасность, существование интерпретатора, права запуска или поддержку длины/аргументов shebang. Прямой запуск отличается от `sh file` и резервного запуска оболочкой. Профиль консервативный, а не спецификация всех POSIX-систем.

Сигнатуры UTF-32 проверяются раньше перекрывающихся UTF-16. Неполные сигнатуры не угадываются. Смещения байтов считаются с нуля, включая BOM. NUL-байты отделены от декодированного NUL.

## Вход и отчёт

```json
{"version":1,"files":[{"path":"greeting.ps1","profiles":["powershell51-script","utf8-no-bom"]}]}
```

Пути CLI относительны `--root` (по умолчанию текущий каталог), пути конфигурации — её каталогу. Режимы нельзя смешивать. Только явные пути: без glob, рекурсии, исключений или подстановки окружения. Повторные нормализованные пути объединяют профили; сортировка детерминирована. Точные ключи обязательны, повторные JSON-ключи запрещены. Конфигурация ограничена 1 MiB и 10 000 записями; каждый файл — 1 MiB по умолчанию, `--max-bytes`: 1–67 108 864.

Абсолютные пути, переход через родителя, Windows-пути с диском/корнем, двоеточия, ссылки, reparse points и не обычные файлы отклоняются. Пробелы и многоязычные имена поддерживаются; перед именем с `-` используйте `--`. POSIX обходит компоненты через дескрипторы без следования ссылкам. В Windows проверки моментальные: это не песочница против злонамеренных одновременных изменений каталога. Используйте стабильную рабочую копию; чтение не создаёт согласованный снимок.

Ограничения относительных путей относятся к записям проверяемых файлов. В `--root` и `--config` допустимы абсолютные пути и `..`, например `--root ..` и `--config ../textport.json`. Проверяется каждый исходный компонент каталога: ссылка, отсутствующий каталог или обычный файл перед `..` отклоняются, а не удаляются нормализацией с выбором другого объекта. Переход к родителю существующего обычного каталога по-прежнему поддерживается.

JSON схемы 1 содержит `files`, `facts`, `results`, `conflicts`, `error`, `summary`, `exit_code`. Машинные ключи и диагностика английские. Исходный текст и абсолютный корень не выводятся; относительные имена и сведения о байтах всё же могут быть приватными. Управляющие символы имён экранируются. Итоги считают результаты потребителей плюс один неизвестный результат на непрочитанный файл.

Коды выхода: 0 — всё совместимо; 1 — есть несовместимость, но нет неизвестных; 2 — ошибка аргументов/конфигурации (stderr, без частичного JSON); 3 — неизвестный результат или неполное чтение, даже при наличии несовместимости. Сообщение о конфликте само код не меняет. [Стабильные ID](diagnostics.md).

## Основания и тесты

[Microsoft](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1), [Linux execve](https://man7.org/linux/man-pages/man2/execve.2.html), [Unicode BOM FAQ](https://www.unicode.org/faq/utf_bom.html). Linux не доказывает поведение всех Unix. Инструмент дополняет BOM-правило PSScriptAnalyzer, pre-commit-hooks и EditorConfig Checker матрицей потребителей; это не форматтер, языковой линтер или определитель кодировки.

```sh
python -m pip install -e .
python -m unittest discover -s tests -v
python tests/runtime_fixtures.py
python -m pip install build
python -m build
```

Проверяются многоязычные байты, UTF-16/32, повреждения/обрыв, NUL, shebang, конфликты, пути/лимиты, стабильный JSON и неизменность исходников. CI отдельно запускает собственные безопасные примеры в Linux напрямую и в настоящем Windows PowerShell 5.1 (ASCII и UTF-8 BOM); поведение без BOM записывается с учётом кодовой страницы. Обычный CLI никогда не запускает пользовательские скрипты. Есть Linux/Windows unit-тесты и установка wheel. Локальный успех Linux не подтверждает Windows CI: проверяйте опубликованный коммит.
